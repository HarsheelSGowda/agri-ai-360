# Database Schema

SQLAlchemy 2.0 declarative models (`backend/app/models/`), created via
`Base.metadata.create_all()` on startup. Works identically against SQLite (local dev default) and
PostgreSQL (set `DATABASE_URL` in `.env`) — no per-database code paths.

## Tables

### `users`
Auth identity only. `id`, `email` (unique), `password_hash` (bcrypt), `created_at`.

### `farmers`
Profile data, 1:1 with `users`. `id`, `user_id` (FK → users, unique), `name`, `location`,
`preferred_language`, `created_at`.

### `farms`
`id`, `farmer_id` (FK → farmers), `name`, `location`, `area_acres`, `soil_type`,
`irrigation_available`, `created_at`.

### `soil_records`
One row per soil submission (history preserved, latest used for current health score).
`id`, `farm_id` (FK → farms), `nitrogen`, `phosphorus`, `potassium`, `ph`, `soil_type`,
`organic_carbon` (nullable), `moisture` (nullable), `electrical_conductivity` (nullable),
`created_at`.

### `weather_records`
Reserved for persisting fetched weather snapshots (schema in place; both the mock provider and the
real `OpenMeteoWeatherProvider` currently return data live without writing to this table — wiring
that up, e.g. to cache live calls or show historical weather trends, is a small follow-up, not
required for the live weather feature to work). `id`, `location`, `temperature_c`, `humidity_pct`, `rainfall_mm`,
`wind_kmh`, `condition`, `source`, `created_at`.

### `crop_predictions`
One row per `/predict/top-crops` call made with a `farm_id`. `id`, `farm_id` (FK → farms),
`model_version_id` (FK → model_versions, nullable), `input_json` (the exact request payload),
`top_crop`, `top_score`, `created_at`.

### `crop_scores`
Top-5 breakdown per prediction. `id`, `prediction_id` (FK → crop_predictions), `crop`,
`probability`, `rank`.

### `recommendation_explanations`
1:1 with a prediction, reserved for persisting a SHAP explanation alongside its prediction (the
`/explain/crop` endpoint currently computes explanations on demand and does not yet persist them
here — see Limitations). `id`, `prediction_id` (FK, unique), `method`, `contributions_json`,
`narrative`.

### `alerts`
Reserved for future proactive notifications (e.g. disease risk, extreme weather). `id`, `farm_id`
(FK → farms), `severity`, `message`, `created_at`.

### `model_versions`
Reserved for a full model registry (currently `models/metrics.json` on disk is the source of
truth for active model + metrics; this table is schema-ready for when model metadata needs to live
in the DB instead of a file, e.g. for multi-tenant model rollout). `id`, `algorithm`, `version`,
`accuracy`, `is_active`, `trained_at`.

### `chat_sessions` / `chat_messages`
Backing store for the AI Agriculture Assistant (`POST /api/assistant/ask`). One session per
farmer (created lazily on first message; `POST /api/assistant/reset` starts a new one).
`chat_sessions`: `id`, `farmer_id` (FK), `created_at`. `chat_messages`: `id`, `session_id` (FK),
`role` (`"farmer"` | `"ai"`), `content`, `created_at`.

### `disease_predictions`
One row per leaf-image diagnosis saved to a farm's history (only written when `POST
/predict/disease` is called with a `farm_id`; a farm-less diagnosis is still returned to the caller
but not persisted). `id`, `farm_id` (FK → farms), `crop`, `condition`, `is_healthy`, `probability`,
`model_used`, `created_at`.

### `market_prices`
Real historical Agmarknet (Government of India mandi) price records, seeded via
`ml/market_price/seed_market_prices.py` from `ml/datasets/agmarknet_prices/*.csv` — calendar year
2016, 6 crops (see `docs/dataset.md`). `id`, `crop`, `state`, `district`, `market`, `variety`,
`group_name` (nullable), `arrivals_tonnes` (nullable), `min_price`, `max_price`, `modal_price`,
`price_date`, `source` (default `"agmarknet_2016_historical"`), `created_at`. Indexed on
`(crop, state, district, market, price_date)` for the lookup patterns `market_price_service.py`
uses.

### `notifications`
Personalized farmer alerts generated by `notification_service.generate_for_farm()` from each
farm's real current soil health, weather, risk, disease and market-price-trend data — never
invented content. `id`, `farmer_id` (FK → farmers), `farm_id` (FK → farms, nullable), `category`
(`WEATHER` | `CROP` | `DISEASE` | `MARKET` | `FERTILIZER` | `WATER` | `RISK`), `priority` (`LOW` |
`MEDIUM` | `HIGH`), `title`, `message`, `is_read`, `created_at`. Deduplicated per farmer on exact
title+message within a 12-hour window so repeated generation doesn't spam duplicates.

### `sensor_readings`
IoT sensor readings (Phase 2E architecture). `source` distinguishes a genuine device push
(`"device"`, written via `POST /api/iot/readings` — a real endpoint any physical gateway could call
today) from a clearly-labeled `"demo_simulation"` row (written via `POST /api/iot/demo/seed`,
used because no physical sensor is connected to this deployment yet). `id`, `farm_id`
(FK → farms), `sensor_type` (`soil_moisture` | `temperature` | `humidity` | `ec`), `value`, `unit`,
`source`, `recorded_at`.

## Migrations

The MVP uses `Base.metadata.create_all()` at startup for fast iteration (safe for SQLite/dev and
for an empty Postgres database). Alembic is a natural next step once the schema needs to evolve
against a database with existing production data — not required for a fresh install of this MVP.
