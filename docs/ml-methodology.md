# ML Methodology

# Part 1 — Crop Recommendation

## Pipeline

```
crop_recommendation.csv
    → cleaning (drop null/duplicate rows)
    → feature selection (N, P, K, temperature, humidity, ph, rainfall)
    → label encoding (22 crop classes)
    → stratified 80/20 train/test split (random_state=42)
    → train 4 classifiers
    → evaluate (accuracy, precision, recall, F1, confusion matrix, 5-fold CV)
    → save models + metrics.json
    → FastAPI loads the active model for inference + SHAP for explanation
```

Implementation: [`ml/crop_recommendation/train.py`](../ml/crop_recommendation/train.py).

## Models trained

| Algorithm | Library | Key hyperparameters |
|---|---|---|
| Random Forest | `sklearn.ensemble.RandomForestClassifier` | 300 trees, unlimited depth |
| Gradient Boosting | `sklearn.ensemble.GradientBoostingClassifier` | scikit-learn defaults |
| XGBoost | `xgboost.XGBClassifier` | 300 trees, depth 6, lr 0.1 |
| SVM | `sklearn.svm.SVC` | RBF kernel, `probability=True` |

All four are trained and saved (`models/*.joblib`) so the Model Lab page can show a genuine
comparison. Only one — the **active model** — is used for live `/predict` and `/explain` calls.
The active model is selected automatically as whichever scored highest test accuracy in the most
recent training run (currently Random Forest); this is recorded in `models/metrics.json` under
`active_model`, not hardcoded in the API.

## Evaluation protocol

- **Split**: stratified 80/20, `random_state=42` for reproducibility.
- **Metrics**: accuracy, weighted precision/recall/F1 (`sklearn.metrics`, `zero_division=0`).
- **Cross-validation**: 5-fold `cross_val_score` (accuracy) on the full dataset, reported alongside
  the held-out test metrics as a sanity check against overfitting to one split.
- **Confusion matrix**: computed on the held-out test set for every model, stored per-algorithm in
  `metrics.json`, rendered for the active model on the Model Lab page.
- **Feature importance**: `model.feature_importances_` for the tree-based models, shown on the
  Model Lab page for whichever model is active.

## Why these results are trustworthy (not fabricated)

- `train.py` is a standalone, runnable script with no hardcoded output — anyone can re-run
  `python ml/crop_recommendation/train.py` and get the same (or very similar, given the fixed
  random seed) numbers.
- The FastAPI layer (`app/services/ml_service.py`) never invents a probability: it calls
  `model.predict_proba()` on the actual loaded `.joblib` model for the actual submitted input.
- If `models/metrics.json` or a `.joblib` file is missing, the API returns
  `503 Service Unavailable` / "Not evaluated yet" in the UI rather than fabricating a number.

## Confidence labeling

`HIGH` ≥ 0.60, `MEDIUM` ≥ 0.30, else `LOW` — applied to the raw `predict_proba` output
(`app/services/ml_service.py::confidence_label`). This is a UI presentation threshold, not a
statement about real-world crop success probability (the UI surfaces this caveat as a tooltip).

# Part 2 — Yield Prediction (Phase 2)

## Pipeline

```
india_crop_production.csv
    → cleaning (drop yield<=0 rows, drop duplicates)
    → feature selection (state, crop, season — year and district intentionally excluded)
    → ordinal-encode 3 categorical features
    → 80/20 train/test split (random_state=42)
    → train 3 regressors (Random Forest, Gradient Boosting, XGBoost — SVR excluded, see below)
    → evaluate (R², MAE, RMSE)
    → save models + yield_metrics.json
    → FastAPI loads the active model + CROP_ALIAS_MAP for /predict/yield
```

Implementation: [`ml/yield_prediction/train.py`](../ml/yield_prediction/train.py).

## Models trained

| Algorithm | Library | Key hyperparameters |
|---|---|---|
| Random Forest | `sklearn.ensemble.RandomForestRegressor` | 200 trees, max depth 18 |
| Gradient Boosting | `sklearn.ensemble.GradientBoostingRegressor` | scikit-learn defaults |
| XGBoost | `xgboost.XGBRegressor` | 300 trees, depth 8, lr 0.1 |

**SVR (Support Vector Regression) was intentionally not trained.** Its training cost scales
quadratically-to-cubically with row count, and this dataset has ~260,000 training rows after the
split — an SVR fit at that scale is impractical for this MVP. This is a deliberate, documented
scope decision, not an oversight.

## Actual results from the last training run

(source of truth: `models/yield_metrics.json`, regenerated by every `train.py` run)

| Algorithm | R² | MAE (t/ha) | RMSE (t/ha) |
|---|--:|--:|--:|
| XGBoost (active) | 0.919 | 1.03 | 3.51 |
| Random Forest | 0.919 | 1.03 | 3.51 |
| Gradient Boosting | 0.793 | 2.09 | 5.63 |

XGBoost was selected as the active model (highest test R²), automatically — not hardcoded.
RMSE is pulled up by a small number of very-high-yield crops in the dataset (e.g. banana, jute,
sugarcane commonly run 10–30+ t/ha vs. ~0.5–2.5 t/ha for most pulses/cereals); MAE is a more
representative error measure across the full crop mix.

## Why these results are trustworthy (not fabricated)

- `train.py` is standalone and runnable — `python ml/yield_prediction/train.py` reproduces these
  numbers (deterministic given `random_state=42`).
- `app/services/yield_service.py::predict_yield` calls `model.predict()` on the actual loaded
  `.joblib` model for the actual submitted (state, crop, season); it never returns a number that
  didn't come from that call.
- An unsupported crop, an unrecognized state, or an unrecognized season returns
  `{"supported": false, "reason": "..."}` — never a guessed number for input the model wasn't
  trained to handle.

## Known methodological limitation (stated plainly)

This model predicts **historical average yield for a (state, crop, season) combination**, not a
forecast for a specific farm in a specific year. It has no access to an individual farm's soil
health, irrigation status, or this season's actual weather — those are the crop-recommendation
model's inputs, not this one's. Treat the output as a regional benchmark to compare against, not a
guarantee. This caveat is shown directly under every yield estimate in the UI.

# Part 3 — Profit Prediction (Phase 2)

## Why this is a calculation, not a "trained profit model"

Profit = Revenue − Cost. Faking a single end-to-end "profit prediction model" would require either
(a) a dataset that honestly links farm-level cost to outcome (none was found — see
`docs/dataset.md`), or (b) inventing plausible-looking cost figures per crop and presenting them as
if they were data-driven. Both are dishonest under this project's own rules. Instead:

```
Revenue = predicted_yield_t_per_ha (real regressor, Part 2)
          x 10                      (t -> quintal)
          x price_rs_per_quintal    (real 2016 Agmarknet median, per crop+state)

Cost     = farmer-supplied Rs./acre (not modeled — see below)

Profit   = Revenue - Cost
```

Implementation: [`app/services/profit_service.py`](../backend/app/services/profit_service.py),
price table built by
[`ml/profit_prediction/build_price_reference.py`](../ml/profit_prediction/build_price_reference.py).

## Why cost is a farmer input, not a model output

Cost of cultivation varies enormously by farm — irrigation method, labor arrangement, whether seed
is farm-saved or purchased, local input prices, mechanization level. No public dataset found during
this project offered farm-level (rather than aggregate/regional) cost figures in a form this app
could honestly generalize from (see `docs/dataset.md` for what was searched and why it wasn't
used). Presenting an invented "typical cost" as a model prediction would violate the project's
explicit "never fabricate" rule. Asking the farmer directly is the honest alternative, and it also
makes the estimate immediately relevant to their actual situation rather than a generic average.

## Supported scope

Profit prediction requires **both** a supported yield estimate (11 crops) **and** price data (6
crops) for the same crop — the intersection is **6 crops**: rice, maize, pigeonpeas, blackgram,
mungbean, lentil. Every other crop returns `{"supported": false, "reason": "..."}` rather than a
guess, at whichever stage (yield or price) is actually missing.

## Why these results are trustworthy (not fabricated)

- `build_price_reference.py` is standalone and rerunnable against the raw CSVs in
  `ml/datasets/agmarknet_prices/` — it doesn't hand-type a single price.
- `profit_service.py::predict_profit` performs one arithmetic calculation from three real inputs
  (model yield, looked-up price, farmer-supplied cost); it never substitutes a placeholder number
  for a missing input — it returns `supported: false` instead.
- Every profit estimate in the UI states its price year, price source (state-specific vs. national
  fallback), and that cost is farmer-supplied — nothing is presented as more authoritative than it
  actually is.

# Part 4 — Water Requirement (Phase 2)

## Formula

```
ETo (mm/day) = p x (0.46 x Tmean + 8)                    [FAO Blaney-Criddle, exact published form]
    p        = FAO Table 4, looked up by (latitude, month), linearly interpolated between
               the table's 5-degree latitude bands
ETc (mm/day) = ETo x Kc_mid(crop)                          [FAO-56 Table 12, mid-season coefficient]
Effective rainfall (mm/day) = USDA SCS formula:
    P <= 250mm:  Peff = P x (125 - 0.2P) / 125
    P  > 250mm:  Peff = 125 + 0.1P
Net irrigation (mm/day) = max(0, ETc - Peff)
```

Implementation: [`app/services/water_service.py`](../backend/app/services/water_service.py).
Reference tables built by
[`ml/water_requirement/build_kc_reference.py`](../ml/water_requirement/build_kc_reference.py) and
[`ml/water_requirement/build_p_reference.py`](../ml/water_requirement/build_p_reference.py).

## Why this isn't a "trained model" either, and why that's the right call here

Crop water requirement is governed by well-established agronomic physics (evapotranspiration
theory), not a pattern to be learned from a dataset — using a published formula with published
reference coefficients *is* the scientifically correct approach, not a shortcut. The only things
this module needed to get right were (a) using the *actual* published formula and tables rather
than an approximation, and (b) being honest about which crops those tables actually cover.

## A documented mistake, corrected in-repo (not just claimed here)

The first implementation approximated FAO's tabulated "p" factor using solar-geometry day length
(`day_length_hours / 12`) instead of looking up the real table, reasoning that day length is a
reasonable physical proxy for "percentage of annual daytime hours." It wasn't: for a July/Nagpur
test case (28°C, ~19°N) it produced **ETo ≈ 22.8 mm/day**, compared to **ETo ≈ 6.2 mm/day** from
FAO's actual Table 4 for the identical input — a ~3.7x error, and physically implausible on its
face (real-world ET₀ essentially never exceeds ~8-10 mm/day). The fix was to fetch FAO's real
Table 4 (the same primary-source-extraction approach used for Table 12 and for the yield/profit
datasets) rather than trust a derivation that merely *sounded* physically reasonable. This is
recorded in `docs/dataset.md` and in `water_service.py`'s own docstring as a durable reminder: a
formula that seems like a correct simplification is still a fabrication risk until it's checked
against the real source it's supposed to approximate.

## Known scope limits

- Only Kc_mid (peak/mid-season demand) is used — not a full growth-stage water-balance curve (no
  planting date is collected).
- Blaney-Criddle is FAO's own "rough estimate only" method, not its recommended Penman-Monteith
  (which needs wind, solar radiation and humidity data this app doesn't collect).
- 17 of 22 recommendation-engine crops are covered; see `docs/dataset.md` for exactly which and why
  the other 5 aren't.

# Part 5 — Yield Risk (Phase 2, ML-based classifier)

## Pipeline

```
india_crop_production.csv (same source as Part 2's yield model)
    -> cleaning (drop yield<=0, drop duplicates, drop crops with <60 records)
    -> per-crop tertile labeling (bottom third=HIGH, middle=MEDIUM, top third=LOW)
    -> feature selection (state, crop, season - year excluded, same reasoning as yield)
    -> ordinal-encode categorical features
    -> TEMPORAL train/test split (train 1997-2015, test 2016-2020 - see below for why)
    -> train 3 classifiers (Random Forest, Gradient Boosting, XGBoost)
    -> evaluate (accuracy, precision, recall, F1, confusion matrix, year-grouped 5-fold CV)
    -> save models + risk_metrics.json
```

Implementation: [`ml/risk_prediction/train.py`](../ml/risk_prediction/train.py).
**Random Forest is the active model: 55.3% test accuracy** on years the model never trained on
(3-class baseline: 33.3%).

## Why the train/test split matters more here than elsewhere in this project

Every other split in this project (crop recommendation, yield, and this model's first draft) used
a random row split. That's fine when each row is closer to independent. It is **not** fine here:
the same (state, crop, season) triple appears in this dataset roughly 20 times — once per year.
A random split puts some of those near-duplicate rows in train and others in test, so a model can
partly memorize `X -> majority label seen in training` instead of learning a generalizable pattern,
and the test accuracy comes out inflated as a result.

**This is exactly what happened on the first attempt**: random-split test accuracy was 64.5%, but
a proper 5-fold CV on the same data came back at 36.9% — barely above chance. That gap is what
gave it away; a single number in isolation wouldn't have. The fix was a temporal split (train on
1997–2015, test on entirely unseen 2016–2020) with year-grouped CV to match. The honest result —
55.3% test accuracy on unseen future years — is real, moderate, and above baseline, which is a
believable outcome for a 3-feature model with no weather/soil/year input predicting something as
volatility-prone as regional yield ranking.

## Sanity check against domain knowledge (not just metrics)

A metric can look reasonable and still be checking the wrong thing, so the model's actual
predictions were spot-checked against something independently known to be true: Punjab is India's
best-known high-yield rice state (heavily irrigated, Green Revolution heartland). The model
predicts rice/Punjab/Kharif as **LOW risk at 100% confidence** and rice/Maharashtra/Kharif (a much
less rice-intensive, more rainfed state) as **HIGH risk at 73% confidence** — matching real
agronomic expectation. This kind of check is why 55.3% accuracy is treated here as a genuine,
if modest, signal rather than dismissed as too low to be useful.

## Relationship to the existing rule-based risk dashboard

This model does **not** replace `app/services/risk_service.py` (the rule-based weather/soil/
water/disease risk summary behind `/app/risk` and `GET /dashboard/{farm_id}`). That system uses
live weather and soil signals a farmer actually controls day-to-day. This model uses none of
that — it answers a narrower, different question ("how has this crop historically performed in
this state and season, nationally?"). Both are surfaced in the app, both are explicitly labeled
for what they measure, and neither is presented as a substitute for the other.
